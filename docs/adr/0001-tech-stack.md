# ADR-0001: Tech stack ของ KamRai

- **สถานะ:** เสนอ (Proposed) — รอ Grand อนุมัติ
- **วันที่:** 2026-10-30
- **ผู้เสนอ:** senior-engineer · **ผู้อนุมัติ:** Grand

## สรุปสำหรับ Grand

- ยืนยันชุดเครื่องมือตามที่เสนอไว้ใน CLAUDE.md: เว็บสร้างด้วย **React + TypeScript** ประกอบด้วย **Vite** อ่าน CSV ด้วย **PapaParse** ทดสอบด้วย **Vitest** และโฮสต์ฟรีบน **Cloudflare** เป็นของนิยม ฟรี หาคนช่วยหรือหาคำตอบได้ง่าย
- ตั้งใจ **ไม่ใช้** อะไรเพิ่มเกินจำเป็น ไม่มี library จัดการเงิน ไม่มีระบบ state ใหญ่ ไม่มี CSS framework ไม่มีตัวจัดหน้าหลายหน้า ข้อมูลในเครื่องเริ่มจาก localStorage อย่างเดียว
- ใส่ "กำแพง" กันข้อมูลหลุดไว้หลายชั้น ได้แก่ กฎ lint ห้ามโค้ดส่งข้อมูลออก, header ความปลอดภัยที่สั่งเบราว์เซอร์ให้บล็อกการส่งข้อมูลออกทุกทาง, และห้ามเปิด analytics ของ Cloudflare
- สิ่งที่แลกมาคือ React หนักกว่าทางเลือกเล็กๆ (เช่น Preact/Svelte) ประมาณ 40–50 KB บนมือถือ ยอมรับได้แลกกับความคุ้นเคยและระบบนิเวศ แต่ตั้งงบขนาดไฟล์ไว้คุม
- **มีเรื่องที่ Grand ต้องตัดสิน 4 ข้อ** อยู่ท้ายเอกสาร (หัวข้อ "คำถามที่รอ Grand ตัดสิน")

## บริบท

KamRai คือเครื่องมือฟรีให้พ่อค้าแม่ค้าออนไลน์ไทยรู้กำไรจริง MVP มี 2 ส่วน: (1) เครื่องคิดราคา/กำไร (2) แดชบอร์ดจาก CSV ที่ผู้ใช้นำเข้าเอง

ข้อกำหนดที่มาจากหลักการผลิตภัณฑ์ใน `CLAUDE.md` และบังคับการเลือก stack:

| หลักการ | ข้อกำหนดทางเทคนิค |
|---|---|
| 1. ฟรี ต้นทุนใกล้ศูนย์ | static site ล้วน (HTML/JS/CSS) ไม่มี server, ไม่มี SSR, ไม่มีฐานข้อมูล · hosting ต้องมี free tier ที่พอใช้จริง |
| 2. ข้อมูลไม่ออกจากเครื่อง | อ่าน CSV และคำนวณในเบราว์เซอร์ · เก็บข้อมูลใน localStorage/IndexedDB · ห้ามมี analytics/third-party script ที่เห็นข้อมูลร้าน · อยากได้กลไกที่ "บังคับ" ได้ ไม่ใช่แค่ขอความร่วมมือ |
| 3. ตัวเลขต้องถูก | เงินเป็นสตางค์ integer · สูตรเป็น pure function ที่เทสต์ได้โดยไม่เปิดเบราว์เซอร์ · ภาษาที่มี type ช่วยกันสับสนหน่วย |
| 4. ใช้ง่าย มือถือก่อน | โหลดเร็วบนมือถือราคาประหยัดและเน็ตช้า · ภาษาไทยแสดงผลถูก · ไม่ต้องสมัคร |
| 5. ไม่ผูกกับไฟล์รูปแบบเดียว | CSV parser ที่ทนไฟล์แปลก (quote, ตัวคั่นต่าง, BOM) · รองรับ encoding ไทยเก่า (TIS-620/Windows-874) · จำ column mapping ไว้ในเครื่อง |
| 6. เรียบง่ายก่อน | dependency น้อย นิยม ดูแลต่อเนื่อง · ทีมคือ Grand + AI agent จึงควรเลือกของที่ AI และชุมชนคุ้นเคยมาก |

## ตัวเลือก

พิจารณาเป็นรายหมวด เฉพาะหมวดที่ย้อนกลับยากหรือกระทบหลักการ

### 1. UI framework

**ตัวเลือก A: React** — ข้อดี: นิยมที่สุด ตัวอย่าง/คำตอบมาก AI agent เขียนได้แม่นที่สุด ระบบนิเวศครบถ้าภายหลังต้องใช้ (เช่น testing library) · ข้อเสีย: runtime ใหญ่กว่าทางเลือกอื่น (react + react-dom ราว 50–60 KB gzip)

**ตัวเลือก B: Preact** — ข้อดี: API แทบเหมือน React แต่เล็กมาก (ราว 4–5 KB gzip) · ข้อเสีย: ใช้ library ของ React ผ่านชั้น compat ซึ่งบางตัวมีจุดไม่เข้ากัน ทีมต้องรู้ความต่าง และคำตอบ/ตัวอย่างน้อยกว่า

**ตัวเลือก C: Svelte** — ข้อดี: bundle เล็ก เขียนสั้น · ข้อเสีย: ระบบนิเวศและความคุ้นเคยของ AI น้อยกว่า React มีการเปลี่ยน syntax ใหญ่ระหว่างเวอร์ชัน (runes) ทำให้ตัวอย่างบนเน็ตปนกันสองแบบ

**ตัวเลือก D: Vue** — ข้อดี: เรียนง่าย เอกสารดี · ข้อเสีย: ไม่ได้เปรียบ React ในงานนี้ และความคุ้นเคยของ AI/ชุมชนไทยน้อยกว่า

**ตัวเลือก E: ไม่ใช้ framework (TypeScript + DOM ล้วน)** — ข้อดี: เล็กที่สุด ไม่มี dependency · ข้อเสีย: หน้าจับคู่คอลัมน์และแดชบอร์ดมี state เยอะ เขียนเองจะยุ่งและบั๊กง่าย ซึ่งขัดกับ "เรียบง่าย" ในแง่การดูแล

### 2. Build tool / meta-framework

**ตัวเลือก A: Vite (SPA)** — ข้อดี: มาตรฐานปัจจุบันของ SPA, เร็ว, ตั้งค่าน้อย, ได้ CSS Modules และ TypeScript มาในตัว, ผล build เป็นไฟล์ static ล้วน · ข้อเสีย: ไม่มี (สำหรับขนาดงานนี้)

**ตัวเลือก B: Next.js (static export)** — ข้อดี: นิยม · ข้อเสีย: ออกแบบมาเพื่อ server rendering ฟีเจอร์หลักหลายอย่างใช้ไม่ได้ใน static export ทำให้มีความซับซ้อนที่ไม่ได้ใช้ และเสี่ยงมีคนเผลอเพิ่ม server code ซึ่งละเมิดหลักการที่ 1

**ตัวเลือก C: Astro** — ข้อดี: เหมาะกับเว็บเนื้อหา ส่ง JS น้อย · ข้อเสีย: แอปเราเป็นเครื่องมือโต้ตอบเกือบทั้งหน้า ข้อได้เปรียบของ Astro จึงแทบไม่ได้ใช้

### 3. ภาษา

**ตัวเลือก A: TypeScript (strict)** — ข้อดี: จับบั๊กก่อนรัน โดยเฉพาะการสับสนหน่วยเงิน (บาท vs สตางค์) และ field ของ CSV ที่อาจว่าง · ข้อเสีย: ต้องเขียน type เพิ่มเล็กน้อย

**ตัวเลือก B: JavaScript** — ข้อดี: ไม่มีขั้น compile type · ข้อเสีย: เสียเกราะป้องกันเรื่องตัวเลข ซึ่งเป็นหัวใจของผลิตภัณฑ์

### 4. CSV parser

**ตัวเลือก A: PapaParse** — ข้อดี: นิยมที่สุดในเบราว์เซอร์, ทน quote/ตัวคั่นต่าง/ขึ้นบรรทัดใน field, เดาตัวคั่นอัตโนมัติ, รองรับ streaming และ Web Worker สำหรับไฟล์ใหญ่, ไม่มี dependency, ไม่ส่งข้อมูลออก · ข้อเสีย: การดูแลโปรเจกต์ช่วงหลังไม่ได้คึกคักมาก (แต่เสถียรและฟีเจอร์ครบสำหรับเรา)

**ตัวเลือก B: d3-dsv** — ข้อดี: เล็ก · ข้อเสีย: ไม่มี streaming/worker ไม่มีเดาตัวคั่น ต้องเขียนส่วนเสริมเอง

**ตัวเลือก C: เขียน parser เอง** — ข้อเสีย: CSV มีกรณีขอบเยอะ (quote ซ้อน, ขึ้นบรรทัดใน field, CRLF) เป็นแหล่งบั๊กที่ไม่จำเป็น

**ตัวเลือก D: csv-parse** — ข้อเสีย: ออกแบบเน้น Node.js ใช้ในเบราว์เซอร์ได้แต่ไม่ใช่ทางหลัก

### 5. Test runner

**ตัวเลือก A: Vitest** — ข้อดี: ใช้ config เดียวกับ Vite, รองรับ TypeScript/ESM ทันที, API คล้าย Jest · ข้อเสีย: ไม่มี

**ตัวเลือก B: Jest** — ข้อเสีย: ต้องตั้งค่าเพิ่มเพื่อให้ทำงานกับ TypeScript/ESM แบบ Vite

### 6. ที่เก็บข้อมูลในเครื่อง

**ตัวเลือก A: localStorage อย่างเดียว (ผ่าน wrapper เล็กๆ ที่เราเขียนเอง)** — ข้อดี: ง่ายที่สุด sync ไม่ต้องใช้ library พอสำหรับข้อมูลเล็ก (ค่าตั้งเครื่องคิดเลข, column mapping, ค่าธรรมเนียมที่ผู้ใช้แก้) · ข้อเสีย: ความจุจำกัด (ราว 5 MB ต่อเว็บ แล้วแต่เบราว์เซอร์) เก็บเป็น string เท่านั้น ไม่เหมาะเก็บออเดอร์หลายหมื่นแถว

**ตัวเลือก B: IndexedDB ผ่าน `idb-keyval`** — ข้อดี: ความจุใหญ่กว่ามาก เก็บ object ได้ library เล็กมาก · ข้อเสีย: เป็น async ทำให้โค้ดซับซ้อนขึ้น และจำเป็นก็ต่อเมื่อเราตัดสินใจเก็บข้อมูลออเดอร์ข้ามการใช้งาน

**ตัวเลือก C: IndexedDB ผ่าน Dexie** — ข้อดี: query ได้ ทำ migration ได้ · ข้อเสีย: เกินความต้องการ MVP มาก

### 7. วิธีจัดการเงิน

**ตัวเลือก A: `number` ที่เป็นจำนวนเต็มสตางค์ + โมดูลเงินเล็กๆ ที่เราเขียนเอง** — ข้อดี: ไม่มี dependency · `Number.MAX_SAFE_INTEGER` สตางค์ ≈ 90 ล้านล้านบาท เกินยอดขายร้านค้าใดๆ มาก · ข้อเสีย: ต้องเขียนฟังก์ชันแปลง/ปัดเศษเองและเทสต์ให้ครบ (ซึ่งเป็นงานที่ต้องทำอยู่แล้วตามหลักการที่ 3)

**ตัวเลือก B: library เงิน (เช่น dinero.js) หรือทศนิยม (เช่น decimal.js, big.js)** — ข้อดี: มีฟังก์ชันสำเร็จรูป · ข้อเสีย: เพิ่ม dependency และ API ที่ต้องเรียน ทั้งที่เรามีสกุลเงินเดียวและการดำเนินการไม่กี่แบบ (บวก ลบ คูณเปอร์เซ็นต์ ปัดเศษ)

**ตัวเลือก C: `bigint`** — ข้อเสีย: ใช้กับ `Math`/`Intl` และ JSON ลำบาก ไม่ได้ประโยชน์เพราะตัวเลขเราไม่ถึงขีดจำกัดของ `number`

### 8. Hosting

**ตัวเลือก A: Cloudflare (Pages หรือ Workers Static Assets)** — ข้อดี: ฟรีสำหรับ static site แบนด์วิดท์ไม่จำกัดสำหรับไฟล์ static, มีจุดให้บริการในไทย, ตั้ง HTTP header เองได้ผ่านไฟล์ `_headers` (จำเป็นสำหรับ CSP), มี preview URL ต่อ PR ให้ Grand กดลองก่อน merge · ข้อเสีย: ต้องระวังไม่เปิด Web Analytics ของ Cloudflare (มันจะฉีด script เข้าหน้าเว็บ)

**ตัวเลือก B: GitHub Pages** — ข้อดี: ฟรี อยู่ที่เดียวกับโค้ด · ข้อเสีย: **ตั้ง HTTP header เองไม่ได้** ทำ CSP ได้แค่ผ่าน `<meta>` ซึ่งใช้บางคำสั่งไม่ได้ (เช่น `frame-ancestors`) และไม่มี preview ต่อ PR ในตัว

**ตัวเลือก C: Netlify** — ข้อดี: ฟีเจอร์ใกล้เคียง Cloudflare (`_headers`, preview ต่อ PR) · ข้อเสีย: free tier มีโควตาแบนด์วิดท์/build ที่จำกัดกว่า ถ้าผู้ใช้โตขึ้นมีโอกาสต้องจ่าย

**ตัวเลือก D: Vercel** — ข้อเสีย: เน้น Next.js/server, เงื่อนไข free tier (Hobby) จำกัดการใช้งาน และไม่ได้เปรียบสำหรับ static site ล้วน

### 9. Styling

**ตัวเลือก A: CSS ธรรมดา + CSS Modules (มีใน Vite อยู่แล้ว) + CSS custom properties สำหรับสี/ระยะ** — ข้อดี: ไม่มี dependency, เบา, ใครก็อ่านออก · ข้อเสีย: ต้องวางระบบชื่อ/ตัวแปรเองนิดหน่อย

**ตัวเลือก B: Tailwind CSS** — ข้อดี: เร็วเวลาเขียน AI เขียนคล่อง · ข้อเสีย: เพิ่มเครื่องมือ build และ class ยาวอ่านยากสำหรับ Grand · ยังไม่มีปัญหาที่ CSS Modules แก้ไม่ได้

**ตัวเลือก C: UI component library (MUI, Chakra ฯลฯ)** — ข้อเสีย: หนักบนมือถือ หน้าตาไม่ใช่ของเรา และ MVP มีหน้าจอไม่กี่หน้า

### 10. ตัวจัดการแพ็กเกจ

**ตัวเลือก A: npm** — ข้อดี: มากับ Node.js ไม่ต้องติดตั้งเพิ่ม เอกสารทุกที่ใช้ npm เป็นค่าตั้งต้น · ข้อเสีย: ช้ากว่า pnpm เล็กน้อย (ไม่มีนัยกับโปรเจกต์ขนาดนี้)

**ตัวเลือก B: pnpm / Yarn / Bun** — ข้อดี: เร็ว ประหยัดดิสก์ · ข้อเสีย: เป็นเครื่องมือเพิ่มอีกตัวที่ Grand ต้องติดตั้งและเข้าใจ โดยไม่มีประโยชน์ชัดเจนสำหรับ repo เดียวขนาดเล็ก

### 11. Lint / format

**ตัวเลือก A: ESLint (flat config ตามเทมเพลต Vite: typescript-eslint + react-hooks) + Prettier** — ข้อดี: มาตรฐาน มากับเทมเพลต Vite อยู่แล้ว เขียนกฎเฉพาะของเราได้ (ดูกฎ privacy ด้านล่าง) · ข้อเสีย: สองเครื่องมือ config สองไฟล์

**ตัวเลือก B: Biome** — ข้อดี: ตัวเดียวทำทั้ง lint และ format เร็วมาก · ข้อเสีย: เขียนกฎเฉพาะ (เช่น ห้ามเรียก API บางตัว) ยืดหยุ่นน้อยกว่า ESLint และไม่ใช่ค่าตั้งต้นของเทมเพลต Vite

### 12. CI

**ตัวเลือก A: GitHub Actions workflow เดียว** รัน `npm ci` → lint → typecheck → test → build ทุก PR และทุก push เข้า `main` · ปล่อยให้ Cloudflare build/deploy เองผ่าน Git integration · ข้อดี: ฟรี ตั้งครั้งเดียว · ข้อเสีย: build ซ้ำสองที่ (GitHub + Cloudflare) ซึ่งรับได้

**ตัวเลือก B: ไม่มี CI พึ่ง agent รันเทสต์เอง** — ข้อเสีย: ไม่มีอะไรรับประกันว่า PR ที่ Grand จะ merge ผ่านเทสต์จริง

## การตัดสินใจ

เลือกชุดต่อไปนี้ ทุกตัวใช้ **major version ล่าสุดที่ stable ณ วันที่ตั้งโปรเจกต์** และล็อกเวอร์ชันจริงไว้ใน `package-lock.json` (ADR นี้จงใจไม่ระบุเลขเวอร์ชันเพื่อไม่ให้เอกสารล้าสมัยหรือเดาผิด — frontend-dev บันทึกเวอร์ชันที่ใช้จริงใน PR ตั้งโปรเจกต์)

| หมวด | เลือก | หมายเหตุ |
|---|---|---|
| UI framework | **React** | ไม่ใช้ router library, ไม่ใช้ state library (ใช้ `useState`/`useReducer`/context ในตัว) |
| Build tool | **Vite** (SPA, เทมเพลต `react-ts`) | ผลลัพธ์เป็นไฟล์ static ใน `dist/` |
| ภาษา | **TypeScript** `strict: true` | เพิ่ม `noUncheckedIndexedAccess` เพราะข้อมูล CSV มักมีช่องว่าง |
| Runtime สำหรับพัฒนา | **Node.js LTS** | ระบุใน `.nvmrc` และ `engines` ของ `package.json` |
| ตัวจัดการแพ็กเกจ | **npm** | commit `package-lock.json` เสมอ · CI ใช้ `npm ci` |
| CSV parser | **PapaParse** | ถอดรหัสไฟล์เองด้วย `TextDecoder` ก่อนส่งเข้า PapaParse (ดูด้านล่าง) |
| Test runner | **Vitest** | เริ่มเทสต์เฉพาะ `src/lib/` (pure function) · ยังไม่ติดตั้ง Testing Library/jsdom/Playwright จนกว่าจะมีเหตุผลจริง |
| ที่เก็บข้อมูลในเครื่อง | **localStorage อย่างเดียว** ผ่าน `src/lib/storage.ts` | ยังไม่ใช้ IndexedDB (รอคำตอบคำถามข้อ 1) |
| เงิน | **สตางค์ integer บน `number`**, ไม่ใช้ library | โมดูล `src/lib/money.ts` ของ finance-logic |
| Hosting | **Cloudflare** (Pages หรือ Workers Static Assets) | **ปิด Web Analytics** · ใช้ `_headers` ตั้ง CSP |
| Styling | **CSS ธรรมดา + CSS Modules + custom properties** | ไม่ใช้ CSS framework / UI library · ฟอนต์ระบบก่อน |
| Lint / format | **ESLint (flat config) + Prettier** | เพิ่มกฎ privacy (ด้านล่าง) |
| CI | **GitHub Actions** workflow เดียว | lint → typecheck → test → build |

### รายละเอียดที่ต้องทำตาม

**โครงโฟลเดอร์เริ่มต้น** (ไม่สร้างโฟลเดอร์ล่วงหน้าถ้ายังไม่มีไฟล์)

```
src/
  lib/        # pure function: เงิน สูตร แปลง CSV → ตัวเลข, storage wrapper — ห้าม import React
  features/
    calculator/
    dashboard/
  App.tsx
public/
  _headers    # security headers สำหรับ Cloudflare
fixtures/     # CSV ตัวอย่าง ข้อมูลสมมติเท่านั้น
```

กฎ: ไฟล์ใน `src/lib/` ห้าม import `react`, ห้ามแตะ DOM/`window` (ยกเว้น `storage.ts` ซึ่งเป็นจุดเดียวที่แตะ localStorage)

**เงิน**
- หน่วยภายในเป็นสตางค์ integer เสมอ ตั้ง type ไว้ให้อ่านชัด เช่น `type Satang = number` (จะทำเป็น branded type เพื่อให้ compiler กันการเอาบาทไปบวกสตางค์ก็ได้ ให้ finance-logic ตัดสินในงานแรก)
- แปลงข้อความจากผู้ใช้/CSV (`"1,234.50"`, `"฿99"`) เป็นสตางค์ด้วยการ parse string **ไม่ผ่าน `parseFloat` แล้วคูณ 100** (เช่น `0.29 * 100` ได้ `28.999999999999996`)
- อัตรา % เก็บเป็น basis points (integer) · การปัดเศษอยู่ในฟังก์ชันเดียว วิธีปัดตามที่ finance-logic กำหนดและอ้าง `research/`
- แสดงผลด้วย `Intl.NumberFormat('th-TH')` ไม่ต้องใช้ library
- ทุกค่าที่เข้าโมดูลเงินตรวจด้วย `Number.isSafeInteger` ในจุดรับข้อมูลเข้า

**CSV และภาษาไทย**
- อ่านไฟล์เป็น `ArrayBuffer` แล้วถอดรหัสด้วย `TextDecoder`: ลอง `utf-8` แบบ `fatal: true` ก่อน (ตัด BOM อัตโนมัติ) ถ้าไม่ผ่านให้ใช้ `windows-874` (ครอบคลุม TIS-620) แล้วให้ผู้ใช้สลับเองได้ถ้าตัวอักษรเพี้ยน — `TextDecoder` มีในทุกเบราว์เซอร์ ไม่ต้องเพิ่ม library
- ไฟล์ใหญ่ (หลายหมื่นแถว) ใช้ PapaParse โหมด worker หรือ chunk เพื่อไม่ให้หน้าค้างบนมือถือ — ถ้าใช้ worker ต้องเพิ่ม `worker-src blob:` ใน CSP
- column mapping ที่ผู้ใช้จับคู่ไว้ เก็บใน localStorage โดยใช้ "ลายนิ้วมือ" ของชุดหัวคอลัมน์เป็น key
- วันที่ (รวม พ.ศ.) แปลงด้วยฟังก์ชันของเราเองใน `src/lib/` ยังไม่ใช้ date library

**ที่เก็บข้อมูล**
- `src/lib/storage.ts` เป็นจุดเดียวที่อ่าน/เขียน localStorage · ทุก key ขึ้นต้น `kamrai:` และเก็บ `schemaVersion` เพื่อ migrate ภายหลัง
- จัดการกรณี localStorage ใช้ไม่ได้ (เช่นโหมดส่วนตัวบางเบราว์เซอร์ หรือเต็ม) โดยแอปยังทำงานได้แค่ไม่จำค่า
- มีฟังก์ชัน "ลบข้อมูลทั้งหมด" ที่ลบทุก key `kamrai:` (รองรับข้อกำหนดของ qa-privacy ว่าต้องลบได้ด้วยปุ่มเดียว)
- **เกณฑ์เปลี่ยนไป IndexedDB:** เมื่อ Grand ตัดสินใจให้แดชบอร์ดจำข้อมูลออเดอร์ข้ามการใช้งาน → เขียน ADR ใหม่ ใช้ `idb-keyval` และเปลี่ยนเฉพาะใน `storage.ts`

**ความเป็นส่วนตัว (บังคับ ไม่ใช่คำแนะนำ)**
1. **ห้าม** analytics, tracker, error-reporting SDK (เช่น Sentry), ฟอนต์/ไอคอน/script จาก CDN ภายนอก (รวม Google Fonts — เพราะทำให้ IP ผู้ใช้ถูกส่งไปบุคคลที่สาม) · ถ้าจะใช้ฟอนต์ไทยพิเศษต้อง self-host ใน repo
2. **ปิด Cloudflare Web Analytics** ในหน้าตั้งค่าโปรเจกต์ และ CSP ด้านล่างจะบล็อกมันอีกชั้นถ้าเผลอเปิด
3. **กฎ ESLint ห้ามช่องทางส่งข้อมูลออก** ใน `src/`: `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, `navigator.sendBeacon` (ใช้ `no-restricted-globals` / `no-restricted-properties`) — ถ้าวันหนึ่งจำเป็นจริงต้องมี ADR และปิดกฎเฉพาะจุดพร้อมคอมเมนต์อ้าง ADR
4. **Security headers ใน `public/_headers`** (ค่าเริ่มต้น ปรับได้ใน PR ตั้งโปรเจกต์ถ้าพบว่า build ต้องการ):

```
/*
  Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data: blob:; font-src 'self'; connect-src 'none'; worker-src 'self' blob:; object-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'
  Referrer-Policy: no-referrer
  X-Content-Type-Options: nosniff
  Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=()
```

   หัวใจคือ `connect-src 'none'` — เบราว์เซอร์จะบล็อก `fetch`/XHR/WebSocket/beacon ทุกตัวในหน้าเว็บ แม้มี dependency ใดแอบส่งข้อมูล ก็ส่งไม่ได้ · ต้องตรวจหลัง deploy ว่าไม่มี CSP error ใน console (ถ้า Vite/React ต้องการ inline style จริงค่อยพิจารณา `'unsafe-inline'` เฉพาะ `style-src` พร้อมเหตุผล)
5. dependency ใหม่ทุกตัวต้องระบุเหตุผลใน PR และ qa-privacy ตรวจว่าไม่มีการส่งข้อมูลออก

**ขนาด bundle บนมือถือ**
- งบเริ่มต้น: **JS ที่โหลดตอนเปิดหน้าแรก ≤ 120 KB gzip** (React ใช้ไปราว ครึ่งหนึ่ง) · CSS ≤ 20 KB gzip
- โหลดแดชบอร์ดและ PapaParse แบบ lazy (`React.lazy` / `import()`) เพื่อให้เครื่องคิดราคาซึ่งเป็นหน้าแรกเปิดได้เร็ว
- CI แสดงขนาดไฟล์หลัง build ทุก PR (ระยะแรกดูจาก output ของ `vite build` ก็พอ ยังไม่ต้องใช้เครื่องมือวัดเพิ่ม) · ถ้าเกินงบ reviewer ถือเป็นระดับ "ต้องแก้"
- ไม่มีกราฟ library ในตอนนี้ — กราฟแดชบอร์ดให้เริ่มจาก CSS/SVG ง่ายๆ ถ้าต้องการ library กราฟจริงให้เสนอ ADR แยก เพราะ library กราฟมักใหญ่

**CI (`.github/workflows/ci.yml`)**
- trigger: `pull_request` และ `push` เข้า `main`
- ขั้นตอน: `npm ci` → `npm run lint` → `npm run typecheck` (`tsc --noEmit`) → `npm test` → `npm run build`
- ใช้ Node เวอร์ชันจาก `.nvmrc`
- ตั้ง branch protection ให้ `main` ต้องผ่าน CI ก่อน merge (Grand เป็นคนกดตั้งใน GitHub)

## ผลที่ตามมา

**ง่ายขึ้น**
- เครื่องมือทุกตัวเป็นค่าตั้งต้นที่นิยมที่สุดในหมวด — agent เขียนได้แม่น หาคำตอบได้ง่าย คนใหม่เข้ามาช่วยได้ทันที
- สูตรเงินแยกอยู่ใน `src/lib/` เทสต์ด้วย Vitest ได้โดยไม่เปิดเบราว์เซอร์
- ความเป็นส่วนตัวถูก "บังคับ" ด้วยเครื่องมือ 3 ชั้น (lint, CSP, review) ไม่ได้พึ่งความจำของคน
- ค่าใช้จ่าย hosting เป็นศูนย์ และ Grand กดลองแต่ละ PR ได้จาก preview URL

**ยากขึ้น / ความเสี่ยง**
- **React หนักกว่าทางเลือก** — ถ้าวัดจริงแล้วหน้าแรกช้าบนมือถือราคาประหยัด ทางหนีคือเปลี่ยนเป็น Preact ผ่าน alias ใน Vite ซึ่งทำได้โดยไม่ต้องเขียนโค้ด UI ใหม่ส่วนใหญ่ ถ้าเราไม่พึ่ง library React ภายนอกมาก (อีกเหตุผลที่ให้ dependency น้อย)
- **CSP เข้มงวดอาจทำให้บางอย่างพังเงียบๆ** เช่นถ้าภายหลังเพิ่ม library ที่ใช้ inline style/script — ต้องเปิด console ตรวจหลังทุก deploy และ qa-privacy ใส่เป็น checklist
- **localStorage จำกัดความจุ** — ถ้าภายหลังต้องเก็บออเดอร์ ต้องย้ายไป IndexedDB (ออกแบบให้เปลี่ยนแค่ `storage.ts`)
- **ข้อมูลอยู่แค่ในเบราว์เซอร์เครื่องนั้น** — ล้าง cache/เปลี่ยนเครื่อง = ข้อมูลหาย · Safari อาจลบข้อมูลเว็บที่ไม่ได้เปิดนานหลายวัน · ควรบอกผู้ใช้บนหน้าจอ และในอนาคตอาจมีปุ่ม export/import ค่าตั้งเป็นไฟล์ (ยังไม่ทำ)
- **PapaParse ดูแลไม่คึกคัก** — ความเสี่ยงต่ำเพราะ CSV เป็นมาตรฐานนิ่ง ถ้าต้องเปลี่ยน ห่อการเรียกไว้ในโมดูลเดียว (`src/lib/csv.ts`) จะเปลี่ยนง่าย
- **Cloudflare เปลี่ยนผลิตภัณฑ์ได้** — Cloudflare กำลังผลักให้โปรเจกต์ใหม่ใช้ Workers Static Assets แทน Pages (ควรตรวจสถานะล่าสุดตอนตั้งค่าจริง) ทั้งสองแบบรองรับ static site และ `_headers` และเนื่องจากเราเป็นไฟล์ static ล้วน ย้ายไปที่อื่น (Netlify ฯลฯ) ได้ในไม่กี่ชั่วโมง

**ต้องทำต่อ (แตกเป็น issue)**
1. ตั้งโปรเจกต์ Vite + React + TS, ESLint/Prettier พร้อมกฎ privacy, Vitest, โครงโฟลเดอร์, `.nvmrc` (frontend-dev)
2. `public/_headers` + ตั้งค่า Cloudflare (ปิด Web Analytics) + ตรวจ CSP บน preview (frontend-dev, ตรวจโดย qa-privacy)
3. GitHub Actions CI + branch protection (frontend-dev ทำ workflow, Grand ตั้ง protection)
4. `src/lib/money.ts` + เทสต์ (finance-logic)
5. อัปเดตส่วน "Stack" ใน `CLAUDE.md` หลัง ADR นี้อนุมัติ

**ควรกลับมาทบทวนเมื่อ**
- หน้าแรกเกินงบ bundle หรือวัดแล้วช้าบนมือถือจริง → พิจารณา Preact
- ต้องเก็บข้อมูลออเดอร์ข้ามการใช้งาน → ADR เรื่อง IndexedDB
- ต้องการใช้งานออฟไลน์/ติดตั้งเป็นแอป (PWA) → ADR แยก (ต้องปรับ CSP สำหรับ service worker)
- จำเป็นต้องมีการเชื่อมต่อเครือข่ายใดๆ → ADR แยก และต้องผ่านหลักการที่ 2

## คำถามที่รอ Grand ตัดสิน

1. **แดชบอร์ดควร "จำ" ข้อมูลออเดอร์ที่นำเข้าไว้ไหม เมื่อปิดแล้วเปิดใหม่?**
   - ข้อเสนอสำหรับ MVP: **ไม่จำ** — จำแค่การจับคู่คอลัมน์ ผู้ใช้นำเข้าไฟล์ใหม่ทุกครั้ง (ใช้เวลาไม่กี่วินาทีเพราะจับคู่ไว้แล้ว) · ข้อดี: ง่ายกว่า และข้อมูลลูกค้า (ชื่อ ที่อยู่) ไม่ค้างอยู่ในเครื่อง ลดความเสี่ยง PDPA กรณีเครื่องใช้ร่วมกัน
   - ถ้าเลือก "จำ": ต้องใช้ IndexedDB + ADR ใหม่ + ต้องมีปุ่มลบข้อมูลและคำเตือนชัดเจน
2. **ชื่อเว็บ (domain):** ใช้ที่อยู่ฟรีของ Cloudflare (เช่น `kamrai.pages.dev`) ไปก่อน หรือซื้อ domain เอง (มีค่าใช้จ่ายรายปี ราคาขึ้นกับนามสกุล ต้องเช็กตอนซื้อ) — ข้อเสนอ: ใช้ของฟรีก่อน ย้ายภายหลังได้
3. **บัญชี Cloudflare และ GitHub เป็นของใคร:** แนะนำให้อยู่ในบัญชีของ Grand เอง (agent ไม่ควรถือสิทธิ์ deploy) และ Grand เปิดใช้ branch protection ของ `main`
4. **ยอมรับ trade-off React vs Preact ไหม:** ข้อเสนอคือใช้ React (คุ้นเคย/เสี่ยงน้อย) แลกกับไฟล์ใหญ่ขึ้นราว 40–50 KB และมีงบขนาดไฟล์คุม — ถ้า Grand ให้ความสำคัญกับความเร็วบนมือถือเครื่องเก่ามากเป็นพิเศษ เริ่มด้วย Preact ได้เลยตั้งแต่ต้น
